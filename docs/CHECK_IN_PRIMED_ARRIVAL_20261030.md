## API additions (backend first)

- `recordCheckInReadinessSampleCallable` optionally returns `arrival: {sessionId,expiresAtMs,latitude,longitude,accuracyMeters,capturedAtMs,here,place}`. It is server-owned evidence on the existing session, not an independent eligibility token. Here still needs30 seconds, Place90. Raw receipt expiry stays20 seconds; qualified arrival has a180-second server lease. Good stationary accurate samples inside the same qualified area can renew the lease. Lease renewal keeps original qualified coordinates/capture timestamp; it never restamps an old OS fix as fresh.
- `bindCheckInReadinessCallable` accepts optional `useQualifiedArrival:true`. That path authenticates the session/owner, requires an unexpired stored arrival, and derives coordinates/accuracy/dwell from that stored evidence. Caller coordinates cannot move/refresh the snapshot. Public targets require Place; private targets require Here. Venue footprint/point distance and the existing50m plus accuracy rule still constrain the target. The existing five-minute one-use target-bound grant and idempotent bind/create flow remain. Missing optional flag retains legacy fresh-fix validation. A repeated matching bind can retrieve its existing unexpired grant even after the original arrival lease ends.
- `createPrivateCheckInPlaceCandidateCallable` accepts optional `readinessSessionId`; this derives the private candidate's point from an unexpired stored Here arrival and current owner/session, ignoring caller coordinates/timestamps. Legacy fresh-location input stays supported. Candidate issuance alone shares nothing and does not authorize create; bind still checks the unexpired arrival. The exact serving atomic20/hour rate record and candidate write are preserved in one transaction. The obsolete outer20/day check is removed, matching the currently serving callable rather than introducing a daily restriction.
- Canonical/discovery calls accept optional `preparation:true`. They return a175m candidate pool for warming during the countdown, with `preparationRadiusMetres:175` on complete and partial responses. The client must require that marker before accepting a prepared pool: an older endpoint can silently ignore the new input and return a narrower legacy list. Legacy responses omit the marker. The client filters the pool against the qualified arrival before claiming ready; final server binding stays strict. External pool is capped at20 and preserves optional public `checkInBoundary` geometry. Legacy selection keeps its existing five-slot policy and strict spatial filtering. This adds no paid provider or new endpoint/infrastructure.
- Preparation canonical lookup does **not** scan the catalog. It uses the existing automatic single-field latitude index for a numeric latitude band of200m around the origin (latitude delta uses conservative110km/degree, clamped at the poles), with limit1001 to detect overflow beyond1000. A separate `latitude >= ''` query includes every legacy string latitude regardless of whitespace/exponent formatting; it has limit501 to detect overflow beyond500. Firestore inequalities compare matching backend types, so these two query families cover the repository's explicit `number|string` coordinate schema without a migration. Longitude is converted and radial distance is checked after retrieval; no longitude/composite index is required. Either overflow fails explicitly with `nearby_gathr_venues_incomplete`, never a silently incomplete ready marker. An unavailable/disabled single-field index propagates as a preparation failure; there is no catalog-scan fallback or index-creation attempt. The unchanged legacy unprepared endpoint retains its old500-document limit.
- Both complete query results have five-minute **per-process/per-Cloud-Run-instance** module-memory caches keyed by Firestore instance, with in-flight promise deduplication. The global legacy-string cache contains public venue fields and no user coordinates or IDs. Numeric cache retains at most eight latitude-band entries. A band is reused only when its stored bounds contain the new origin's entire required175m latitude band; every response reruns radial distance and mirror-expiry checks. Empty complete results are reusable, while failed/incomplete results are not cached. No per-user candidate IDs, check-in evidence, private labels or whole venue documents enter these caches. New or differently scaled instances start cold, and separately deployed canonical/discovery callables can have different containers. Caches are an optimization, not a coverage assumption or a guaranteed cross-callable read reduction.
- If a venue changes from cached string coordinates to a numeric record before the legacy cache expires, results are deduplicated by document ID and the numeric entry takes precedence. This prevents duplicate picker rows during normalization without a data migration.
- The frontend's normal warming uses one combined discovery response for both GathR and OpenStreetMap choices, not parallel canonical/discovery calls. Cold preparation issues two bounded Firestore queries, returning at most1001 numeric plus501 legacy documents (1502 before explicit cap failure). Within the same warm backend process, a new numeric band with a warm legacy cache issues one bounded query; a same-covered-band retry within TTL issues zero canonical queries. After TTL expiry it issues both again. An explicit discovery retry or standalone canonical fallback can land on a different cold container and therefore incur the full bounded pair; cross-callable zero-read reuse is **not** a production guarantee. The frontend's own retained prepared results avoid an API call entirely on the normal ready-tap path. Empty queries have Firestore's minimum read accounting; these are query/document-count budgets, not a pricing estimate. A latitude stripe can contain geographically distant venues, and a large legacy population can still hit the explicit caps: no live count or serving index availability was verified. Existing OSM provider attempts and20/day server discovery limit remain unchanged.
- OpenStreetMap attempts keep their existing two providers,8s query timeout,10s per-provider HTTP deadline, filtering and safe diagnostics. On all-provider failure, valid canonical candidates survive with `externalLookupStatus:'partial_unavailable'`; legacy unprepared requests with no canonical choices retain the typed retryable unavailable error. Prepared requests instead return the complete marked canonical pool even when empty, with explicit external failure. A successful empty response is `complete`, not an outage. Callable forwarding retains only structured public domain-error details.

## Stationary and departure policy

The30/90-second dwell,0.7m/s stationary threshold,20m prequalification anchor and5m/s driving threshold remain. Accuracy26–50m pauses Place evidence rather than erasing earned time; >50m pauses both within the existing bounded five-minute uncertainty interval. Neither bad endpoint earns time. A fresh return with unknown speed after an inaccurate displaced fix establishes a baseline without losing counters or crediting the bad interval.

Once a server arrival exists, one low-accuracy fix or isolated speed spike does not erase it or extend its lease. Clear departure is an accuracy<=50m sample whose distance from the qualified point minus the larger of current/arrival uncertainty exceeds50m. Vehicle movement is corroborated by two samples with speed>=5m/s no more than60 seconds apart, both accuracy<=50m, and displacement minus maximum uncertainty>20m. These conditions revoke the arrival; driving applies the existing30-second suppression. Changing session/reset, owner, consumption or expiry also makes it unusable. This is a bounded foreground arrival assertion, not background tracking or proof of being indoors.

The360/hour readiness,30/hour bind and20/day discovery limits are unchanged; private candidate creation preserves its currently serving atomic20/hour limit. The frontend must deduplicate/cache warming and sample less often after qualification to stay within those limits. Do not retry a provider at every GPS sample. Later discovery retries must use a genuinely fresh raw fix, because original arrival capture time may exceed the60-second lookup input freshness window; qualified bind/private creation intentionally use the separate server lease. A prepared OSM outage returns the complete canonical pool with `partial_unavailable` and the175m capability marker even when that canonical pool is empty. Legacy unprepared outage behavior with no usable canonical records remains a typed retryable error.

Schema/query evidence: `functions/src/types/index.ts` explicitly declares VenueData latitude/longitude as `number|string`. `venueMirror.ts` normalizes new mirror coordinates but merges and can omit coordinate fields, so it does not prove all older records numeric. The installed Firebase SDK4.17.1 `common-BiV89iPa.cjs.js:3351–3355` matches ordinary inequalities only for equal backend type order, consistent with the official [FieldFilter source](https://github.com/firebase/firebase-js-sdk/blob/main/packages/firestore/src/core/filter.ts). The existing [automatic single-field index contract](https://firebase.google.com/docs/firestore/query-data/index-overview) supports this one-field range query; the exact serving index state was not read. No geohash or universally normalized coordinate field was found, and no schema/index/data migration was introduced.
